# Technical Note: AI Is Optional Everywhere — and P0.1 (Auto-Capture) Uses No AI At All

**Companion to:** `ux-audit-v2-image-data-richness.md` (recommendation P0.1) and `ux-audit-supplier-retailer-flows.md` (the CSV bulk-upload design).
**Purpose:** (1) double-confirm, with code evidence, that AI is optional both for attribute entry today and in the CSV bulk-upload design; (2) explain **why and how** P0.1 — auto-capturing width, height, DPI, file size, and file type at staging — requires zero AI.

---

## 1. Confirmed: AI is optional for attributes in the current wizard

The interactive wizard can be completed end-to-end, with every attribute populated, without AI ever running. Four independent guarantees in the code:

1. **AI never runs unless explicitly clicked.** Extraction fires only from the "Extract Extended Attributes with AI" button, which stays disabled until a category *and* brick are chosen (`image-upload-wizard.tsx:2844`). There is no automatic or background extraction anywhere in the app.
2. **A first-class skip path exists.** "Skip AI Extraction" (`image-upload-wizard.tsx:2848-2850`) sets `aiSkipped` and collapses the AI card to a one-line notice ("AI extraction skipped. You can continue entering attributes manually.", `:2800-2803`). It is reversible via a "Show" button (`:2791-2794`) — skipping costs nothing and locks nothing.
3. **Step gating never consults AI state.** The only conditions to advance are target/location/files (`canProceedStep2`, `:1402-1406`) and the three required manual attributes — image type, purpose, orientation (`canProceedStep3`, `:1415-1417`). No AI field, flag, or result participates in validation; submission (`:3269-3275`) additionally requires only the syndication acknowledgement.
4. **Even the AI's failure mode is manual entry.** On extraction error the UI offers "Continue manually" (`:2890-2892`); every AI suggestion requires an explicit per-row Accept before it counts (`:792, 946-953`); and manual dropdowns/inputs cover every field the AI can suggest (`renderAiResultsCard` edit path, `:890-934`, backed by the same curated GS1 code lists).

**Conclusion:** AI in the attribute flow is an accelerator layered on top of a complete manual path — never a dependency.

## 2. Confirmed: AI is optional in the CSV bulk-upload design

The CSV design in the v1 audit makes the same guarantee explicitly, in three places:

- The upload flow's classification step is titled **"Categorize & extract — optional, not a gate"**: a merchandiser "can skip straight to [review & submit], submit rows as-is, and run AI classification/extraction later, per product" (v1 audit §P0.1, step 4).
- The classification section states outright: **"CSV submission (insert/update/delete) never blocks on classification"** (v1 audit §P0.1a, "Two entry points, one waterfall").
- The guardrails include a standing escape hatch: **"'Skip AI for this group' always available — manual attribute entry exactly as today. Skipping the whole Categorize stage at upload time is equally valid"** (v1 audit §P0.1a, guardrails).

Structurally this holds because the 21-field CSV spec itself contains **no AI-derived field**: every column (action, image_level, product/item_number, file_name, orientation, location_type, …) is supplier-supplied data. AI only ever adds *extra* extended attributes on top; the CSV round-trip is complete without it.

**Conclusion:** in both the current product and the proposed CSV design, a supplier who never touches AI loses nothing except the optional extended-attribute suggestions.

## 3. Why P0.1 requires no AI: decoding is not inference

P0.1 proposes auto-filling **width, height, pixel density (DPI), file size, and file type** the moment a file is staged. The reason this needs no AI is categorical, not incidental:

> **AI infers facts that are *not* in the data. P0.1 reads facts that are *literally stored in the file*.**

An image file is a container format. Its dimensions are not a property a model must judge from pixels — they are header fields the *decoder itself* must read before it can render a single pixel. The same is true of density metadata (DPI), byte size, and MIME type. Extracting them is **decoding** (deterministic, exact, defined by file-format specifications), not **inference** (probabilistic, confidence-scored, occasionally wrong).

Practical consequences of that distinction:

| Property | AI extraction | P0.1 decoding |
|---|---|---|
| Accuracy | probabilistic; needs confidence + human review | exact by definition — the decoder that renders the preview uses the same numbers |
| Cost | per-call model cost | zero |
| Latency | seconds, network round-trip | milliseconds, fully client-side |
| Offline / privacy | image bytes leave the browser | nothing leaves the browser |
| Failure mode | plausible-but-wrong values | value present or absent — never invented |
| Review burden | Accept/Reject per suggestion | none; values are facts, shown read-only |

Using AI for these fields wouldn't just be unnecessary — it would be **strictly worse**: a vision model asked "what are this image's pixel dimensions?" can hallucinate a plausible number, while `naturalWidth` cannot. This is why P0.1 renders the values as read-only "measured" data with no Accept/Reject ceremony: there is nothing to review.

## 4. How it works: the exact browser mechanisms

Everything below is standard Web-platform API plus a few dozen lines of byte-level parsing. No libraries, no server round-trip, no model.

### 4.1 File size and file type — already done today

The `File` object handed to the drop/browse handlers carries both:

```ts
file.size  // exact byte count
file.type  // MIME type, e.g. "image/jpeg"
```

The wizard already stores these at staging (`processFiles`, `image-upload-wizard.tsx:1043-1051`: `size: file.size, type: file.type`) and displays them on the post-submit card. **This existing behavior is the proof of pattern for P0.1** — nobody would suggest AI to read `file.size`; width and height are the same class of fact, one layer deeper in the same file.

### 4.2 Pixel width and height — the decoder already knows

The wizard already creates a preview for every staged file (`URL.createObjectURL(file)`, `:1049`) and renders it in an `<img>`. The browser therefore *already decodes the image header*. Reading dimensions is asking the decoder for numbers it has:

```ts
// Preferred: decode without attaching anything to the DOM
const bmp = await createImageBitmap(file)
const { width, height } = bmp   // exact pixel dimensions
bmp.close()

// Fallback (older engines): the preview path we already use
const img = new Image()
img.src = URL.createObjectURL(file)
await img.decode()
const width = img.naturalWidth, height = img.naturalHeight
```

For JPEG specifically, these values come from the SOF (Start of Frame) segment of the file — two big-endian 16-bit integers. They are not estimated; they are the canvas the format instructs the decoder to allocate.

### 4.3 DPI (pixel density) — a header field, parsed with a `DataView`

Density metadata lives in well-specified header locations. A JPEG file is a sequence of segments, each tagged with a two-byte marker (`0xFFxx`) and a length. Two segments can carry density:

**JFIF APP0 segment** (marker `0xFFE0`, identifier `"JFIF\0"`) — the payload layout after the identifier is fixed:

| Offset in payload | Field | Meaning |
|---|---|---|
| +7 | `units` (1 byte) | 0 = aspect ratio only, **1 = dots/inch**, 2 = dots/cm |
| +8 | `Xdensity` (2 bytes, big-endian) | horizontal density |
| +10 | `Ydensity` (2 bytes, big-endian) | vertical density |

`units=1 → dpi = Xdensity`; `units=2 → dpi = Xdensity × 2.54`.

**EXIF APP1 segment** (marker `0xFFE1`, identifier `"Exif\0\0"`) — a TIFF structure whose IFD0 entries include:

| Tag | Field | Type |
|---|---|---|
| `0x011A` | XResolution | RATIONAL (numerator/denominator, 2 × uint32) |
| `0x011B` | YResolution | RATIONAL |
| `0x0128` | ResolutionUnit | SHORT — 2 = inch, 3 = cm |

The TIFF header declares its own byte order (`II` little-endian / `MM` big-endian), which the parser must honor. `dpi = XResolution`, converted ×2.54 when the unit is cm.

Both are read the same way — no decoding of pixel data at all, just a scan of the first few KB:

```ts
const buf = await file.slice(0, 128 * 1024).arrayBuffer()
const view = new DataView(buf)
// verify SOI (0xFFD8), then walk segments: marker (2B) + length (2B) + payload,
// stopping at SOS (0xFFDA); inspect APP0/APP1 payloads per the tables above.
```

**PNG** (accepted by current validation until the spec's JPG-only rule lands, v2 audit P0.4): the `pHYs` chunk stores pixels-per-metre as two uint32s plus a unit byte; `dpi = ppm × 0.0254`.
**WebP**: carries no standard print-density field — the parser returns `null` and the DPI field simply stays blank, which is the correct honest outcome (never invent a value).

The complete parser is ~60–80 lines of dependency-free TypeScript operating on an `ArrayBuffer`. It is the same logic every image viewer executes when it shows "300 dpi" in a file-info panel.

### 4.4 Failure semantics — the opposite of AI's

The utility never throws and never guesses. If a file is truncated, exotic, or missing density metadata, the affected field resolves to `null` and the UI shows an empty measured value. Compare the failure modes: AI's worst case is a **confident wrong answer** requiring human review to catch; decoding's worst case is an **honest blank**. For master data syndicated to retailers, that asymmetry is the whole argument.

### 4.5 Where it plugs in

- `processFiles` (staging) and the replace-image commit both call `measureImageFile(file)`; results attach to the staged file record by id.
- The three manual number inputs for DPI/Height/Width in the attributes form are replaced by a read-only "measured from file" display — removing both the friction (v2 audit finding C2) and a correctness bug: as manual *shared* attributes, one typed height was applied to every image under "apply to all," which is wrong whenever files differ (same family as finding C3).
- The metadata export reads the measured values, so the numbers a retailer receives are the numbers the decoder found — not what a human remembered to type.

---

## 5. Summary

- **Attributes today:** fully completable manually; AI is click-to-run, skippable, reversible, and absent from all validation gates. Confirmed in code.
- **CSV design:** classification/extraction is explicitly "optional, not a gate"; submission never blocks on AI; the 21-field spec contains no AI-derived column. Confirmed in the design text and its field spec.
- **P0.1:** needs no AI because it performs deterministic decoding of values stored in the file — via `File.size`/`File.type`, `createImageBitmap`/`naturalWidth`, and a small header parser for JFIF/EXIF/pHYs density fields. AI could only add cost, latency, and the risk of confidently wrong numbers to facts the browser already knows exactly.
